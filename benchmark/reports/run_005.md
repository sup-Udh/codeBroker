# Benchmark Report

## Task
task_005.md — Discovery Stress Test

## Objective
Evaluate CodeBroker's repository discovery without relying on filenames or symbol names, and without manual repository browsing.

## Tools Used
- generate_context_capsule (4 natural-language queries: auth, real-time collaboration, room management, notifications)
- search_codebase (keyword: notification, websocket, auth, room [path_scope=api], supabase — mode=both)
- find_symbol (addNotification)

No manual file browsing was performed prior to or during discovery, per the task's constraint.

## Most Useful Tool
`search_codebase` in `mode=both` for **specific, narrow** terms. `keyword="notification"` correctly and immediately found both the `Notification` type and `addNotification` function (High/Medium confidence) in `RoomContext.tsx` — succeeding exactly where the semantic capsule query for the same concept failed (see below). `keyword="room", path_scope="api"` cleanly found `generateRoomId` in the rooms API route.

## Least Useful Tool
`generate_context_capsule` for broad conceptual queries. Two semantically distinct natural-language queries — "real-time collaboration between multiple users editing simultaneously" and "notification infrastructure for alerting users of events" — returned **byte-for-byte identical results**: the same `User` interface, the same `server/websocket.ts::user` local variable (itself a low-value match — a local variable named `user`, not a meaningful symbol) duplicated twice, and the same two unrelated profile-page skeletons. Two unrelated queries collapsing onto an identical, marginally-relevant result set indicates the semantic embedding fallback is not meaningfully discriminating between these queries, or a caching key collision. Neither result actually surfaced the real collaboration infrastructure (`server/websocket.ts`'s broadcast/connection logic, `RoomProvider`'s awareness/cursor sync) or the real notification logic (`addNotification`, `Notification` type) that `search_codebase` found trivially with the narrower keyword in a follow-up call.

## Search Failures
1. **"auth" discovery failure**: `search_codebase(keyword="auth", mode=both)` returned exactly one low-relevance result (`checkAuth` in a browser-extension popup script) and completely missed the actual authentication system: `app/login/page.tsx` (Google OAuth login), `app/auth/callback/route.ts`, and `utils/supabase/{client,server,admin}.ts` (the `createClient`/`createAdminClient` functions — independently confirmed as top architectural hotspots in task_001, with 18 and 10 incoming edges respectively). This is a significant miss given how central these functions are to the codebase.
2. **"supabase" discovery failure**: `search_codebase(keyword="supabase", mode=both)` surfaced only `package.json` dependency entries and a `test_supabase.js` scratch file — it missed the actual `utils/supabase/client.ts`, `server.ts`, and `admin.ts` files entirely, even though the literal substring "supabase" is present in their file paths. Both of these point to the same underlying authentication subsystem being effectively invisible to keyword discovery unless the searcher already knows to query for `createClient`/`createAdminClient` by name (which defeats the purpose of a discovery stress test).
3. The `generate_context_capsule` duplicate-result issue above.

## Discovery Failures
The cumulative effect of (1) and (2): **the authentication system, arguably the most security-relevant subsystem in the app, was not discoverable through any of the natural-language or generic-keyword queries I tried.** It was only discoverable by already knowing the exact function names (`createClient`, `createAdminClient`) from the prior architectural audit (task_001). For a genuine "discover the auth system, starting cold" stress test, this is a failure of the core discovery promise.

## Context Failures
N/A — once symbols were found (e.g., `addNotification`), `find_symbol`'s returned preview was accurate and sufficient.

## Graph Failures
N/A — graph tools weren't in scope for this task.

## Missing Functionality
1. `generate_context_capsule`'s semantic fallback needs better discrimination between distinct conceptual queries — returning identical results for "real-time collaboration" and "notifications" suggests either a stale cache keyed too coarsely, or an embedding space too coarse to separate these concepts in this repo's symbol set.
2. Keyword search for domain words that appear in **directory/path names** but not as semantically "auth-flavored" symbol names (`createClient`, `signInWithOAuth`) should weight path-substring matches higher — a developer asking "where's the auth system" by domain term should not have a worse hit rate than someone who already knows the function name.

## Native Tool Fallbacks
None — per the task's constraint, no manual browsing was used; all gaps above are reported as discovery failures rather than worked around.

## Token Efficiency
Mixed. The successful keyword searches were extremely cheap (~50-150 tokens each). The capsule queries were comparatively expensive (return full pivot implementations) while being the least reliable — the worst token-value tradeoff observed across all five benchmark tasks.

## Estimated Tokens Retrieved
~1,800 tokens across 7 calls.

## Estimated Tokens Avoided
Low for this task specifically — because discovery partially failed, the net token "savings" claim is weaker than other tasks. Had I been forced to fall back to manual exploration to find the auth system (which the task explicitly disallowed), it would have cost ~2,000–3,000 tokens to read `utils/supabase/*.ts` and `app/login/page.tsx` directly — roughly comparable to what was already spent failing to find them via search.

## Suggested Improvements
1. Investigate why two distinct natural-language queries to `generate_context_capsule` produced byte-identical results — likely a semantic-fallback or caching bug that defeats the purpose of natural-language discovery.
2. Improve "auth"/"supabase"-style domain-term discovery: weight directory-path substring matches and well-known auth-provider call patterns (`signInWithOAuth`, `createClient` from `@supabase/*`) higher in symbol-name keyword search, since these are exactly the terms a developer unfamiliar with the codebase would type first.
3. Consider a "concept index" pass at indexing time that tags symbols with domain concepts (auth, realtime, notifications, rooms) independent of literal name/path matching, so natural-language discovery doesn't depend entirely on embedding quality or literal substrings.
