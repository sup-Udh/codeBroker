# Benchmark Report

## Task
task_001.md — Full Repository Architectural Audit

## Objective
Determine whether CodeBroker can accurately explain a large repository (target: `link-up`, a real-time collaborative coding-interview/LeetCode-style room app) without requiring significant manual exploration.

## Tools Used
- get_workspace
- project_overview
- repository_stats
- project_overview_ai
- architectural_hotspots
- dependency_cycles
- subsystem_stats (×2: "rooms", "problem-engine")
- subsystem_overview ("problem-engine")
- graph_subtree (root_symbol=useRoom, depth=2, markdown)

All mandatory tools for this task were used. No native fallback tools (grep/Read) were required at any point.

## Most Useful Tool
`graph_subtree` on the top hotspot (`useRoom`). One call surfaced the entire room-feature component tree (50 nodes, 59 edges) — every component that consumes the central `RoomContext`, plus the handlers they call. This single call did the work of opening ~14 files manually and cross-referencing imports.

Close second: `architectural_hotspots`, which correctly identified `useRoom` (25 incoming edges) as the dominant hub — a genuinely correct architectural signal, since the room context is the real coordination point of a collaborative-editor app.

## Least Useful Tool
`project_overview_ai`. The narrative was generic boilerplate ("showcases a well-structured web application... conducive to ongoing development and scalability") that added no information beyond what `project_overview`'s raw directory/file counts already implied. It read as a templated LLM summary rather than an architecturally grounded one. It did add value once per subsystem (`subsystem_overview` was more specific than the repo-wide version), but the repo-wide AI overview specifically was low-signal for the token cost.

## Search Failures
None — this task didn't exercise `search_codebase`.

## Discovery Failures
- No dedicated "repository entrypoints" tool exists. Requirement #3 (identify entrypoints) had to be reconstructed manually by calling `subsystem_stats` per-subsystem and reading its `entrypoints`/`routes` field. There is no single call that lists all entrypoints repo-wide (e.g., all API routes, all page.tsx files) without already knowing subsystem names to query.
- "Most critical files" (requirement #6) has no direct file-level scoring. `architectural_hotspots` scores symbols, not files, so file criticality had to be inferred by eyeballing which files repeatedly appeared among top symbols (`RoomContext.tsx`, `utils/supabase/admin.ts`). A `file`-level hotspot aggregation would close this gap.

## Context Failures
None significant. Subsystem stats accurately listed files, symbols, dependencies, and consumers for both `rooms` and `problem-engine` with no apparent omissions (cross-checked file lists felt complete and consistent with directory counts from `project_overview`).

## Graph Failures
`dependency_cycles` returned 0 cycles. Plausible for a 109-file repo with disciplined unidirectional imports, but it's an unfalsifiable result without independent verification — a known limitation is that this tool can't be sanity-checked without manual inspection, and a benchmark task like this should ideally include a repo with a planted cycle to confirm true-positive detection.

## Missing Functionality
1. No repo-wide entrypoint enumeration tool (independent of subsystem_name guesses).
2. No file-level (as opposed to symbol-level) hotspot/criticality ranking.
3. No direct "how do subsystems X and Y communicate" tool — had to manually diff the `consumers`/`dependencies` arrays of two `subsystem_stats` calls to infer cross-subsystem communication (this directly foreshadows task_003's harder version of the same gap).

## Native Tool Fallbacks
None required.

## Token Efficiency
Excellent. Total CodeBroker output across 9 calls was on the order of a few thousand tokens (project_overview alone reported its own `approx_tokens: 354`). Manually achieving equivalent understanding would require opening and reading most of the 32 problem-engine files plus ~14 room-related components — likely 15–25k+ tokens of raw file content.

## Estimated Tokens Retrieved
~6,000–7,000 tokens across all 9 calls (combined JSON/markdown payload sizes).

## Estimated Tokens Avoided
~18,000–25,000 tokens (avoided reading ~46 source files directly to get equivalent structural understanding).

## Suggested Improvements
1. Add a repo-wide `list_entrypoints` tool (API routes, page components, CLI mains) so requirement #3-style questions don't require subsystem-name guessing.
2. Add file-level hotspot aggregation alongside symbol-level `architectural_hotspots`.
3. Add a `subsystem_communication(a, b)` tool that directly diffs two subsystems' dependency/consumer sets instead of requiring two separate `subsystem_stats` calls and manual correlation.
4. Make `project_overview_ai`'s repo-wide narrative less templated/generic — it currently provides little beyond what's inferable from `project_overview`'s raw counts.
