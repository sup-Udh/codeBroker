# Benchmark Report

## Task
task_002.md — Real Feature Implementation Workflow

## Objective
Implement a medium-complexity feature (chosen: add Dart as a supported language to the `link-up` problem-engine wrapper system) and evaluate whether CodeBroker provides enough discovery/context to safely modify production code.

## Tools Used
- generate_context_capsule ("add a new programming language wrapper to the problem engine")
- search_codebase (keyword="language", mode=both; keyword="getAvailableLanguages", mode=text; keyword="dart", mode=text)
- find_symbol (SUPPORTED_LANGUAGES)
- get_context (LanguageConfig, markdown)
- get_edit_context (generateWrapper)
- impact_analysis (getAvailableLanguages, structured)
- read_file_skeleton (starterCode.ts, adapters/index.ts, dart.ts after creation)
- read_file_snippet (api/run/route.ts)

Native fallback used: plain `Read` on `app/api/run/route.ts` and `app/lib/languages.ts` — see Context Failures below for why.

## Most Useful Tool
`generate_context_capsule`. One call returned the full `generateWrapper` dispatcher plus two complete reference implementations (cpp, java) and 7 more skeletonized sibling wrappers — everything needed to know the exact pattern to replicate for a new language, with zero manual file-opening.

## Least Useful Tool
`impact_analysis` on `getAvailableLanguages`. It returned an empty `callers`/`reverse_dependencies` — technically correct (verified by a follow-up `search_codebase` text search confirming the function really is unused), but the tool gave no indication of *why* it had nothing to report or that it had exhaustively checked. A zero-result impact analysis is indistinguishable from "tool found nothing" vs. "tool confirms truly unused" without a manual sanity-check call.

## Search Failures
`search_codebase("language", mode=both)` and `generate_context_capsule("add a new programming language wrapper")` both **missed** two of the most decision-relevant artifacts in the entire task:
1. `LEETCODE_SLUG_MAP` in `starterCode.ts`, which already contained a `dart: "dart"` entry — meaning a previous developer had partially started this exact feature.
2. The explicit disable check in `app/api/run/route.ts` (`if (langInfo.id === "dart" || langInfo.id === "kotlin")`) which **already special-cased "dart" by string literal**, before "dart" was ever added to `SUPPORTED_LANGUAGES` or the wrapper registry.

Both of these were only found by manually reading `app/api/run/route.ts` in full and by a later confirmatory `search_codebase(keyword="dart", mode=text)` pass. This is a significant finding for a real-world coding task: discovery surfaced the generic pattern (how to add a wrapper) but missed the specific pre-existing partial implementation and the business-logic constraint (Wandbox doesn't support a Dart compiler, so execution is intentionally disabled) that materially changes the risk profile of the change. Had I trusted CodeBroker's discovery alone and not opened the consumer file, I'd have shipped a "supported" language that was already silently blocked at the API layer — a correct outcome by luck (Kotlin precedent), not by tool guidance.

## Discovery Failures
None beyond the search failure above — `find_symbol` and `get_context` worked exactly as expected for known symbol names.

## Context Failures
`get_edit_context(generateWrapper)` correctly listed `app/api/run/route.ts` as the sole reverse dependency, but only as a file path — it did not surface that this consuming file contains a hard-coded language-id disable list. A tool whose stated purpose is "the context required to safely modify a symbol" should ideally have flagged that the consumer contains conditional logic keyed on the very same string values (`"dart"`, `"kotlin"`) being added. This forced a manual `Read` of the full file to catch a project-breaking assumption.

## Graph Failures
None applicable to this task — `explore_graph`/`graph_subtree` weren't strictly required since `get_edit_context` already gave forward/reverse dependencies directly.

## Missing Functionality
- No "find all string-literal references to this identifier value" capability — i.e., searching for the literal `"dart"` as a future language-id before it existed in the symbol graph wasn't something any graph tool could have caught (it only existed as an un-typed string literal, not a symbol). `search_codebase(mode=text)` is the closest workaround, but it's not used automatically as part of `get_edit_context`'s consumer analysis.
- `impact_analysis` should distinguish "verified zero impact" from "no impact found, but graph coverage may be incomplete."

## Native Tool Fallbacks
Two: a full `Read` of `app/api/run/route.ts` (to find the disable-list business logic) and `app/lib/languages.ts` (to see the existing array literal before editing it). Both were necessary because the CodeBroker tools surfaced the *symbol* but not enough raw surrounding logic to make an informed edit safely.

## Token Efficiency
Good but not perfect. `generate_context_capsule` and `get_edit_context` were efficient (estimated ~1,200 combined tokens) and replaced what would have been ~10 file opens. However, the two manual `Read` fallbacks (full files) added back some of the token cost that targeted tools are meant to avoid — directly because targeted tools didn't surface the consumer's internal logic.

## Estimated Tokens Retrieved
~4,500 tokens (capsule + edit context + impact analysis + skeletons + 2 manual file reads).

## Estimated Tokens Avoided
~9,000–12,000 tokens (avoided reading all 14 existing wrapper files plus adapters/providers in full).

## Suggested Improvements
1. `get_edit_context` should optionally include a text-search pass over reverse-dependency files for the symbol's own literal arguments (e.g., language-id strings) to catch consumer-side conditional logic keyed on those values.
2. `generate_context_capsule` and `search_codebase` should weight/include partial or "stub" matches (like `LEETCODE_SLUG_MAP`'s pre-existing `dart` entry) more aggressively — a feature query like "add a new language" should proactively check whether any existing artifacts already reference that prospective new value.
3. `impact_analysis` zero-result responses should state explicitly whether the search was exhaustive (e.g., "0 callers found across N indexed symbols") vs. an empty/degenerate result.
