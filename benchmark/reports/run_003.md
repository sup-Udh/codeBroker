# Benchmark Report

## Task
task_003.md — Deep Dependency Investigation

## Objective
Investigate the relationship between two major subsystems — chosen: the **rooms** subsystem (`RoomContext.tsx`/`useRoom`/`RoomProvider`, the real-time collaborative editor) and the **problem-engine** subsystem (`normalizeProblem`, `generateWrapper`, `judge`) — to evaluate graph quality, dependency tracing accuracy, and architectural understanding.

## Tools Used
- shortest_path (useRoom→normalizeProblem; useRoom→judge; RoomProvider→generateWrapper; POST→normalizeProblem)
- explore_graph (RoomProvider, depth 2, outgoing)
- architectural_hotspots (path_scope=problem-engine)
- get_context (POST in api/run/route.ts)
- read_symbol_source (runCode, native-adjacent but via CodeBroker)
- subsystem_stats (reused from task_001 findings on "rooms"/"problem-engine")

## Most Useful Tool
`shortest_path`, specifically because its **negative** results were architecturally meaningful. `shortest_path(useRoom → normalizeProblem)` and `shortest_path(RoomProvider → generateWrapper)` both returned `found: false`. Rather than a graph gap, this is the *correct* answer: the rooms subsystem talks to the problem-engine over an HTTP boundary (`fetch("/api/run")` inside `runCode`), not a static function call. Once I retargeted the query at the actual connector (`POST` in `app/api/run/route.ts`), `shortest_path(POST → normalizeProblem)` immediately resolved with distance 1. This is the central architectural finding of the task: **the two subsystems are decoupled by a network boundary, and the route handler is the sole connector symbol.**

## Least Useful Tool
`explore_graph` on `RoomProvider`. It returned a same-file-dominated subtree (8/8 nodes in `RoomContext.tsx`) with an automatic warning that the tool itself flagged as likely co-location noise rather than real architecture. Useful that it self-flagged, but it didn't surface anything connecting to the problem-engine subsystem — consistent with the network-boundary finding, but as a standalone call it was low-signal.

## Search Failures
None — search tools weren't the focus this task.

## Discovery Failures
None — `subsystem_stats` from task_001 already correctly listed `RoomContext.tsx` as a consumer of `problem-engine`, which was the right initial signal pointing at this relationship, even though it doesn't show *how* (direct call vs. HTTP).

## Context Failures
A real gap: `shortest_path`'s `found: false` response gives **no signal about why** — it's indistinguishable from "genuinely unrelated," "missing edge due to indexing gap," and "related only through a non-static-call boundary (HTTP/IPC/etc.)," which are three very different and consequential answers for an engineer. I had to manually hypothesize the HTTP boundary and verify it by reading `runCode`'s source directly — CodeBroker didn't suggest this on its own.

## Graph Failures
None once redirected at the correct connector (`POST`). The graph itself is accurate — `POST`'s callee list (`getSlugForRoom`, `fetchLeetCodeProblem`, `normalizeProblem`, `getAdapterCode`, `generateWrapper`, `judge`) correctly captures the full problem-engine pipeline invoked per code execution.

## Missing Functionality
No tool detects or annotates **network/IPC boundaries** (fetch calls, WebSocket sends) as a distinct edge type connecting otherwise graph-disconnected subsystems. Given this repo's architecture (client components calling Next.js API routes via `fetch`), this is a first-class relationship type that's currently invisible to the dependency graph — `fetch("/api/run")` is just a string literal to the indexer, not an edge to the `POST` handler in that route file. A "logical connector" inference step (matching fetch URL string literals to route file paths) would have shortened this investigation by at least 2 calls.

## Native Tool Fallbacks
None strictly required — `read_symbol_source` (a CodeBroker tool) was sufficient to confirm the HTTP-boundary hypothesis instead of falling back to plain `Read`.

## Token Efficiency
Very good. The entire investigation, including two "failed" exploratory shortest_path calls, totaled well under 1,500 tokens, and arrived at a precise, falsifiable architectural conclusion (HTTP boundary, single connector symbol `POST`).

## Suggested Improvements
1. `shortest_path`'s `found: false` response should distinguish "no path exists in the indexed graph" from "one or both endpoints have zero edges at all" — and ideally suggest nearby candidate connector symbols (e.g., sibling route handlers in the same directory as a fetch target) when a literal URL string matching a known route is detected in the source symbol.
2. Add a "logical edge" inference pass that resolves `fetch("/api/...")` call sites to the corresponding Next.js route handler (`POST`/`GET`/etc. in `app/api/.../route.ts`), exposing client→API-route relationships as first-class graph edges instead of requiring the user to manually guess and re-query.
