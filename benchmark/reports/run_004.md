# Benchmark Report

## Task
task_004.md — Refactoring & Duplicate Logic Audit

## Objective
Evaluate CodeBroker's ability to discover duplication, estimate refactor risk, and prepare safe code changes.

## Tools Used
- find_duplicate_logic (repo-wide)
- impact_analysis (TestCaseResult — triggered ambiguity path)
- get_edit_context (TestCaseResult, disambiguated by file_path)
- read_symbol_source (TestCaseResult in problem-engine/types.ts)
- generate_patch (TestCaseResult consolidation)

## Most Useful Tool
`find_duplicate_logic`. In one call it surfaced 19 groups spanning a wide quality range: real cross-file near-duplicates worth consolidating (5 wrapper-generator families differing only by target-language syntax; 5 `*Type` transpiler functions; a duplicated `TestCaseResult` interface; a duplicated `Room` type across two profile pages) down to trivial near-duplicates (single-line RoomContext handler functions like `kickUser`/`rejectUser`/`approveUser` that are one-liners and not worth merging). This is exactly the raw material a refactor audit needs.

## Least Useful Tool / Most Concerning Finding
**`find_duplicate_logic` produced false-positive "duplicate" groups that are actually a single symbol matched against itself.** The first 6 "exact, cross_file: false" groups (`getFunctionAdapterCode`, `getLinkedListAdapterCode`, `getTreeAdapterCode`, `getDesignAdapterCode`, `getGraphAdapterCode`, `getAdapterCode`) each list **two members with identical file_path AND identical start_line/end_line** — i.e., the same definition counted twice as if it were two distinct duplicate occurrences. This isn't duplicate logic at all; it's a self-match bug in the detector. A naive consumer of this report would think there are 6 genuine duplicate-function pairs requiring consolidation when there are zero — these are single, unique functions.

## Search Failures
N/A (find_duplicate_logic is deterministic, not a search tool).

## Discovery Failures
The self-duplicate bug above is a discovery-correctness failure, not a coverage gap — it actively produces misleading positive results rather than missing things.

## Context Failures
`impact_analysis(TestCaseResult)` correctly refused to guess given two same-named symbols and returned a clean `ambiguous: true` with both candidates — good defensive behavior, no complaint here.

`generate_patch` is the deeper context failure: I deliberately instructed it to remove `RoomContext.tsx`'s `TestCaseResult` interface and import the "structurally identical" one from `problem-engine/types.ts` — a claim it had no way to verify from the instruction text alone. The two interfaces are **not** actually identical: `problem-engine/types.ts`'s version has an additional optional field (`executionTime?: number`) that `RoomContext.tsx`'s version lacks. `generate_patch` produced the diff without flagging this discrepancy anywhere (its `introduced_identifiers` field was empty, and the diff/rendered_diff carried no warning). The consolidation happens to be safe only because the differing field is optional — pure luck, not verification. A patch tool operating on "duplicate" types should diff the two definitions itself before complying with a merge instruction, rather than trusting the caller's premise.

## Graph Failures
None observed — `get_edit_context`'s disambiguation via `file_path` substring worked correctly and returned accurate forward/reverse dependencies for the targeted symbol only.

## Missing Functionality
1. `find_duplicate_logic` needs a same-symbol/self-match guard — it should never report a single definition against itself as a duplicate pair.
2. `generate_patch`, when the instruction implies two symbols are equivalent (merging/aliasing), should structurally diff the source/target before applying the instruction and surface any field-level discrepancy as a warning rather than silently complying.

## Native Tool Fallbacks
None required for this task.

## Token Efficiency
Strong for discovery (`find_duplicate_logic`'s one call replaced what would otherwise require diffing dozens of files pairwise). Weak ROI on the patch step given the false confidence it can produce without manual verification — I had to manually read both `TestCaseResult` definitions myself to catch the field mismatch, which is exactly the work the patch tool should have done.

## Suggested Improvements
1. Fix the self-match bug in `find_duplicate_logic` — deduplicate by `(symbol_name, file_path, start_line)` before grouping so a single definition can never appear as both members of a pair.
2. Have `generate_patch` perform a structural pre-check when an instruction implies two named symbols are interchangeable (e.g., diff their fields/signatures) and emit a warning in the response if they're not in fact identical, rather than silently trusting the instruction.
3. Surface a confidence/risk tier per duplicate group (e.g., "verified identical" vs. "near-duplicate, manual review required") so refactor-plan consumers don't have to manually re-verify every group themselves.
